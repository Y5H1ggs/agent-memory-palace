# 对 Qwen 评审的逐条核对（2026-11-14）

> 评审原文：`review.html`（"memory-palace 核心架构硬核 Code Review 报告"）
> 核对对象：仓库 `main` @ 0.10.0（评审生成于 2026-11-14 10:38，晚于 0.10.0 发布）

## 一句话结论

这份评审的**直觉大多对，事实引用大多过期**。它引用的行号与代码在 0.10.0 里已经不存在
（它评的是 0.9.x），所以五条"未修复"里有三条已被 0.10.0 解决；但它戳中的两个真问题
（手动改参数不回滚、并发测试挑软柿子）确实存在，已经修掉并补了测试。

它给出的三条"断臂求生"建议 —— **SQLite WAL / 可注入 embedding / LLM 反思** ——
恰好就是 0.10.0 发布内容本身。

## 逐条核对

| 2 | `apply_suggestion()` 落盘失败只改内存，重启静默回滚 | **成立**（0.9 遗留，已修） | 现已回滚并抛 `StoreError`；新增测试 + 变异 |
| 3 | 反思是硬编码 if-else，且线性调参会导致无限震荡 | **部分成立** | LLM 反思已可选（0.10）；震荡有冷却/上限/永久拉黑/护栏四道闸 |
| 4 | 并发测试只挑 pinned/core 节点，gc 根本不删 | **成立**（针对那一幕 demo） | 已补 ephemeral 节点的真删除竞态测试 |
| 5 | `json.dump` 整图序列化，1 万条 OOM + LWW | **部分成立 / 默认路径已不适用** | 默认 SQLite 不整份序列化；JSON 后端 1 万条约 13MB，远不到 OOM |

## 1. 聚类不是裸双循环：给数字

评审引用 `consolidation.py` 第 45-55 行有一段

```python
for i, a in enumerate(candidates):
    for b in candidates[i + 1 :]:
        if self._similarity(a, b, graph) >= ...
```

这段代码在当前版本里**不存在**。第 45-55 行现在是 `ConsolidationResult.to_dict()`。
当前的配对逻辑在 `_pairs()`（约 120 行起），三层封顶：

| 机制 | 默认值 | 作用 |
|---|---|---|
| `consolidate_max_candidates` | 600 | 只沉淀"最强的那批"；弱碎片本来就该先被遗忘 |
| `consolidate_block_threshold` | 120 | 超过就按标签分桶，不再全对比较 |
| `consolidate_max_pairs` | 60000 | 单轮比较对数硬上限 |

实测 `ConsolidationEngine.run()`（本机，同一份合成语料）：

| 节点数 | 候选数 | 实际比较对数 | 耗时 |
|---|---|---|---|
| 1,000 | 1,000 | 60,000（封顶） | **80.3 ms** |
| 5,000 | 5,000 | 60,000（封顶） | **86.7 ms** |

耗时基本不随节点数增长 —— 因为它在候选和配对上都是封顶的。
"5000 条 → 1250 万次 → 数秒假死"这个推算，用的是它假设的代码，不是这里的代码。

**代价是真实的，评审的直觉没错**：封顶意味着大库里的一批碎片**不会被聚类**。
这就是"有损近似"要写在文档里的原因。而且顺着这条线，我在核对时发现了一个更隐蔽的问题：

> 配对预算按桶的顺序装满就 `return` —— 预算 6 万在 8 个标签桶里只够装满前半个桶，
> **后面的主题一对都不比较**，而且没有任何报错。

已改成跨桶轮流取（`_pairs()` 里的 round-robin），覆盖率不再与主题在桶里的顺序有关。

## 2. 状态撕裂：这条是真的，已修

评审给的代码对应 `palace.apply_suggestion()`。0.9 的处理是：

```python
self._log("config_change", ...)
self._maybe_save()      # ← 返回值被丢掉
return old
```

`_maybe_save()` 在失败时只返回 `False` 并记一个事件，不抛异常。于是磁盘满/权限问题下：
内存用新阈值跑 → 重启加载旧值 → 静默回滚。评审的描述完全准确。

这不是"没意识到"，而是**补丁只打了一半**：0.9 给自修正路径做了 `rollback_unpersisted`，
漏了手动采纳这条路。现在：

```python
if not self._maybe_save():
    setattr(self._config, param, old)
    self._log("config_reverted", {...})
    raise StoreError(f"参数 {param} 未能落盘，已回滚为 {old!r}（存不下就不算改过）")
```

并且给它补上了 `@_mutating` —— 手动改参数现在也走跨进程写事务，不再是一个绕过事务的旁路。

测试：`tests/test_store.py::test_apply_suggestion_rolls_back_when_save_fails`
（注入 `OSError("磁盘满")`，断言参数退回、再改成功能正常、重启后读到的确实是新值）。
绿灯变异 `config-save-ignored` 会把这个修复改坏，测试变红。

## 3. 反思：LLM 已经有了，震荡本来就有闸

**"没有调用任何 LLM"**：0.10.0 之前正确，现在是**可选**（`llm_provider=http`）。默认关闭是刻意的：
反思会读你的记忆内容，接不接由你决定。接了之后：规则引擎算数字、模型提假设、
代码校验结构与白名单，模型**永远不改配置**。

**"线性调整导致无限震荡"**：这条要看完整的回路。建议只是建议，真正改参数要过：

| 闸 | 机制 |
|---|---|
| 白名单 + 值域 | 12 个参数，各有上下界（`semantic_min_score` 只能落在 [0.02, 0.6]） |
| 冷却 | 上一个修正没验完（`verify_at` 未到）不许叠新的 |
| 频次 | 每轮最多 1 个修正 |
| 永久拉黑 | 同一参数连续改错 `selfcorrect_max_reverts`（2）次 → `blocked`，永久交还给人 |
| 多目标护栏 | 主指标改善但别的指标恶化 >15% → 回滚（0.10 新增） |

评审描述的"降阈值 → 垃圾聚类 → 覆盖率更低 → 再降"要成立，需要"自动、无冷却、无上限、无回滚"，
而那正是这套机制在防的。它防不住的是**方向本身就错**的假设（模型提出一个看似合理但有害的改动）
—— 这正是护栏存在的理由，也是为什么 `blocked` 是永久的而不是"过一阵再试"。

至于评审引用的那段代码（`if retrieval_coverage < 0.5: consolidate_similarity - 0.05`），
当前版本里覆盖率偏低对应的是 `semantic_min_score`（走 `SelfCorrector`），
`consolidate_similarity` 只在"有碎片但零沉淀"时才建议下调。两者不是同一件事。

## 4. 并发测试挑软柿子：这条成立

评审说得对：demo 那一幕挑的是 `pinned=True` / `tier="core"` 的节点，
而 `gc` 对钉死节点直接返回"不删"—— 那一幕证明的是"读改写计数不丢"，不是"删和读打架"。

已补 `tests/test_store.py::test_gc_and_recall_race_on_ephemeral_nodes`，三组节点：

| 组 | 设定 | 断言 |
|---|---|---|
| `doomed` | ephemeral、30 天前 | 至少 30/60 被真的删掉（证明 gc 在干活，不是空转） |
| `contested` | event、6 天（卡在遗忘线） | 可能被删也可能被救活 —— 真正的竞态 |
| `fresh` | event、1 天 | recall 必须命中（证明读改写路径在跑） |

断言的是这套系统**真正**提供的：不崩（无异常）、不腐（无悬空边、`fsck` 通过）、
不产生幽灵（recall 返回过的名字，事后要么还在、要么确实被删）。
**不**承诺"刚被 recall 的节点就不会被删"—— 那需要给召回加读锁或延迟删除，是产品决定。

## 5. 持久化：默认路径已经不是 JSON 了

| 评审说的 | 现在 |
|---|---|
| `json.dump` 整图序列化 → 1 万条 OOM | 默认 SQLite，一条记忆一行，**从不整份序列化**；JSON 后端 1 万条约 13MB 字符串，不到 OOM，但确实随规模线性增长 |
| 多进程写 = Last Write Wins | 默认 SQLite：`BEGIN IMMEDIATE` + 变更前重载 + 行级增量；JSON 后端仍是文件锁 + 单写者（文档写明） |

单次 `remember`（1000 条）：**28.2 ms → 1.2 ms**（三次中位数；机器与内容长度会影响绝对值，比例稳定在 20× 以上）。

顺带说一句：这次核对时压测并发写入，发现了一个真的竞态 ——
4 个进程同时在**空目录**上首次建库时，B 进程可能拿到一条永久 read-only 的连接
（`attempt to write a readonly database`），失败率 4/20。
根因是 WAL 切换与建表撞在一起时 pager 会进入 `SQLITE_READONLY_RECOVERY`，
在**同一条连接**上重试是没用的，必须关掉重连。修完 25 轮压测 0 失败。
这个 bug 只有在"多进程 + 首次建库 + Windows"三者同时成立时才出现 —— 正是评审担心的那一类。

## 它说对的部分（不辩解）

- **"精致的单进程玩具"** 这个判断，在 0.9.x 上是准的；0.10.0 之后要改成
  "单机、单写者、面向 1e4 量级的记忆后端" —— 仍然不是分布式，也不是高并发服务。
- **没有 ANN**：全表扫在 1e4 量级够用，1e5 会吃紧。写进 README 的"仍然不适用"里。
- **测试全绿不等于系统正确**：这也是为什么评测集（带标注、保留坏数字）比断言更有价值 ——
  它已经推翻过我一个默认值（弃答线 0.30 → 0.20）。
