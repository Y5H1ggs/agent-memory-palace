# 同类项目调研与融合判断

> **时效声明**：本文写于 0.5.x（2026-11-13），表格里的能力判断是**当时**的。
> 此后已经补上 SQLite/WAL 后端、跨进程写事务、可替换的嵌入通道、六领域评测集与 LLM 反思。
> 机器可读的现状 → [llms.txt](../llms.txt)；人读的现状 → [README](../README.md)。
> 保留原文不改，是因为「当时为什么这么判断」本身也是记录。

> 调研时间：2026-11-13。目的不是"抄功能"，而是回答一个问题：
> **这套东西缺的到底是能力，还是我没想到的问题。**
>
> 结论先行：补了三处**语义层空白**（双时态、弃答、写入去重），

## 一、竞品地图（按「赌什么」分类，不按功能数量）

| 项目 | 核心赌注 | 记忆的形态 | 授权 / 部署 | 值得借鉴 | 不该借鉴 |
|---|---|---|---|---|---|
| **Mem0** | 记忆是**可复用组件**，不该绑定 runtime | 抽取后的"事实"+ 实体链接（可选图） | Apache-2.0，SDK，自托管 / 云 | 写入端抽取、去重、多租户 scope | 用 LLM 抽事实（破零依赖） |
| **Zep / Graphiti** | 变化才是信号 | **双时态知识图**：每条事实带有效区间，冲突时 invalidate 而非 delete | Graphiti Apache-2.0；Zep 已无社区版 | **valid_from / valid_to / supersede** | 上 Neo4j（本机图够用） |
| **Letta（原 MemGPT）** | 记忆是 agent 的一部分，不是服务 | OS 式分层：core（在上下文）/ recall / archival | Apache-2.0，自托管 / 云 | 分层、自编辑、sleep-time 整理 | 全量 core memory 常驻（预算会被吃光） |
| **Cognee** | 图 + 向量 + 关系一次建好 | ECL 管道（Extract → Cognify → Load） | Apache-2.0，Postgres 单机可跑 | 管道化的写入期加工 | 依赖 Postgres / 图库 |
| **LangMem** | 语义 / 情景 / 程序三类记忆 | LangGraph Store 上的原语 | MIT，库 | 三类划分（本库 five kinds 已覆盖） | 绑 LangChain |
| **TencentDB Agent Memory** | 记忆是**四类资产**，要能被团队共用 | Chat Memory / Skill / Wiki / CodeGraph，L0–L3 分层，BM25+向量+RRF，硬预算，ACL | MIT，Docker 一键 | **L0–L3 分层**、**预算硬约束**、Proxy 零改造接入、RRF 融合 | 团队 ACL / 面板（SaaS 范畴） |
| **progressive-memory（技能）** | 索引先行，按需取全文 | Markdown 索引表 + 每日文件，**每条标 token 成本** | 技能（Claude Skills 生态） | **索引里标代价**，让 agent 自己算 ROI | 纯文件、无衰减无遗忘 |
| **mcp-memory-service** | 一个自托管服务，所有 agent 共用 | 因果知识图（causes / fixes / contradicts），REST + MCP + OAuth | 开源，自托管 | 因果边类型、agent 作用域、SSE | 服务化部署（本库刻意做成零依赖库） |
| **官方 knowledge-graph memory** | 最小可用的实体-关系记忆 | entities / relations / observations（JSONL） | MIT | 三原语的极简性 | 无时间、无衰减、无遗忘 |

一句话总结这个市场：**大家都在解决"存和取"，很少有人解决"什么时候该不取、什么时候该忘、这条还能不能信"**。
后三件正是本库的立足点 —— 但对照下来，它在"什么时候该不取"上其实也没做到位（见 §三）。

## 三、本轮真正补的三处（都不是"加功能"，是补语义漏洞）

### 1. 双时态：旧事实**到期**，而不是被删

原来的做法：用户改主意 → 要么新写一条（旧的还在，检索时两句一起端给模型，让它自己猜哪句作数），
要么 `drop()` 删掉（"我上个月确实这么想过"这个事实也没了）。两种都不对。

现在：`remember(..., supersedes=["旧名"])` → 旧节点 `valid_to = now`、`superseded_by = 新名`。

- 默认检索只返回**当前有效**的（`is_valid_at(now)`）；
- `recall(as_of=...)` / `--as-of 30d` 回看"当时为真的是什么"；
- 失效节点不进重要性账本、不进结构读数、不参与沉淀 —— 否则一条三个月前改掉的偏好会继续污染熵和注入排序；
- 失效节点不按价值 GC，而是按 `history_retention_days`（默认 90 天）回收，进墓碑仍可 restore。

**为什么不做成"删掉旧的"**：删掉以后就无法回答"当时是怎么定的"，
而这类问题在实际使用中很常见（"我们之前为什么用 A 不用 B"）。
**为什么不做成"留着不标"**：两句话并排出现时，模型没有依据判断哪句作数，
它会挑更像当前语境的那句 —— 这就是幻觉的入口。

### 2. 弃答：不知道时说不知道

LongMemEval 把 abstention 单列成一档能力，而本库原来**必然给东西**：
无关问题也会把"当前最重要的两条"端上去当背景。这在 agent 场景里是危险的 ——
用户问"周末去哪玩"，注入块里塞着"半凯利仓位"，模型就可能顺着这条编。

现在 `build_context` 用两层判据：

```
绝对：语义分 ≥ abstain_semantic_floor（0.30）
相对：还要 ≥ 最高分 × semantic_relative_floor，挤掉"字面沾边"
```

不过线 → `abstain=True`，注入块写"（没有相关记忆。不要凭印象补全…）"，
并且**只保留钉死的硬规则**（规则与问题无关也要遵守，这不叫猜）。

**这个阈值不是拍出来的**：实测本库 bigram 编码在无关查询上的底噪 ≤0.13，
真匹配 0.83–0.91，相差一个量级；0.30 落在空档里。它也随语料漂移，所以是配置项不是常数。

### 3. 写入去重：只抓"同一句话说两遍"

不做去重时，同一个结论记三次就有三个节点，检索时互相挤占预算，权重还各自衰减。
现在 `merge=True`（CLI / MCP / HTTP 默认开，库层默认关）：
内容与已有节点余弦 ≥0.92 **且** 长度相近 → 合并（强化 + 标签并集），不新建。

**这里踩到一个真坑，值得单独说**：
`"单笔不超过总资金三分之一"` 与 `"单笔不超过总资金三分之一，且最多同时持三只"` 的余弦是 **0.927**——
只按余弦判，后者（补了新约束）会被前者吞掉，**静默丢失信息**。
所以去重必须再加一条长度比 ≥0.85。余弦对"短句是长句子集"不敏感，这是它的结构性缺陷，不是调参能解决的。

这一条正好说明：**"语义相近"和"重复"是两件事，前者恰恰不该合并。**

## 四、明确拒绝的五项（写了理由，因为"我们不做"也需要依据）

1. **用 LLM 抽取事实**（Mem0 / Cognee 的核心）
   代价：引入模型依赖、不可离线、抽取结果不可审计（错的事实一样进库）。
   本库赌的是"写入由调用方负责，系统只负责筛、忘、讲"。这是设计选择，不是能力缺失。
2. **上图数据库**（Neo4j / FalkorDB）
   本库的图是内存 dict + 邻接，几百到几千节点够用，且能整体序列化成一个 JSON。
   换成图库只换来"看起来专业"，代价是部署复杂度与原子写失效。
3. **换真实 embedding**
   零依赖是它能被任何 agent 直接 `pip install` 的前提。
   但必须承认天花板：bigram 对同义改写、英文、代码符号几乎无效（见 §五）。
4. **core memory 全量常驻**（Letta）
   已用"钉死优先 + 预算"证明更好：硬规则必在，其余按需，避免每轮付全额 token。
5. **多租户 / ACL / Web 面板**（TencentDB / mcp-memory-service）
   那是服务端产品的职责。本库输出的是**可嵌入的记忆语义**，不是运营平台。

## 五、还没做、但应该做的（按性价比排序）

### ① 组件级评测集 —— 最大的空白，也是最该补的

业界现状（这是 2026 年公开的批判，不是我的臆测）：**LoCoMo / LongMemEval 已经出现"评测腐化"**：

- LoCoMo 全文仅约 26k tokens，128k 上下文可直接塞下 → 高分可能测的是长上下文阅读理解，不是记忆；
- 独立审计发现 LoCoMo **约 6.4% 的答案键本身是错的**，且标准 judge 在答案"听起来合理"时经常放行；
- 主流做法只看**端到端 QA 准确率**，从不检查"记忆库里到底存了什么、检索对不对"；
- 规模一拉到 BEAM 的 1M / 10M tokens，所有系统都难看（Mem0 自报 10M 时 48.6）。

所以**不能拿别人的分数当基准**，只能自己建一个组件级评测，测四件业界不测的事：

| 轴 | 怎么测 | 本库现在有读数吗 |
|---|---|---|
| 检索质量 | 标注 50 条真实记忆 + 20 条查询，算 recall@k / MRR | ❌ 只有 coverage 代理指标 |
| 知识更新 | 造 N 次"改主意"，测旧事实是否停止返回、as_of 是否正确 | ✅ 已有断言（`test_temporal.py`） |
| 弃答 | 无关查询的假阳性率 | ✅ 已有断言，但无数据集 |
| 遗忘正确性 | 该忘的忘了没、不该忘的留住没（而不是"总分高不高"） | ⚠️ 只有单点断言 |

**这是下一步唯一值得先做的事**。没有它，"召回够不够用"永远只能靠感觉。

### ② 混合检索 + RRF

现在注入排序用的是手工权重 `0.6×语义 + 0.4×重要性`。TencentDB 与多数竞品用
**BM25 + 向量 + RRF（reciprocal rank fusion）** —— RRF 的好处是**无参数**，
不用为不同语料调权重，且对"专有名词 / ID / 代码符号"这类 bigram 语义几乎失效的查询更稳。

改动不大（加一路字符 n-gram 词法分 + 排名融合），但会动到所有既有排序断言，
需要连带重测，所以本轮没做 —— **不是没想到，是排在评测集之后**。

### ③ 索引里标 token 代价

progressive-memory 的做法值得学：索引行直接写"~80 tokens"，
让 agent 自己判断"取这条值不值"。本库的树状注入只给总预算，没给单条代价。
小改动，等 ②。

## 六、这次调研最该记住的一句

> 竞品的 README 都在列"我支持什么"，而真正决定体验的是**它选择不做什么**。
>
> Mem0 不做 runtime、Letta 不做框架无关、Zep 不做社区版 —— 都是有代价的取舍。
> 本库的取舍是：**零依赖 + 可解释 + 会忘**。
> 0.10 补上了 embedding 通道（可接真模型）与多进程写；仍然没有服务化与分布式。

所以融合的正确姿势不是"把大家的功能都加上"，
而是**只补那些不破坏取舍、又能堵住语义漏洞的部分** —— 双时态、弃答、去重正好属于这类：
它们都只是内存里多几个字段、检索时多一个判断，**没有引入任何新依赖**。
